# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

This repository hosts Ansible automation to build a Debian 13 (trixie) VM for a standalone ESXi host (no vCenter) via a fully unattended (preseed) install, including generating and distributing SSH keys. Networking is DHCP. First target VM: `debian-vm`, sudo user `charlie`, no password on that account at all (locked, SSH-key-only, passwordless `NOPASSWD` sudo).

**Deliberately does not use any vSphere/ESXi API** — no `pyvmomi`, no `community.vmware`. An earlier version drove ESXi through that collection and hit a chain of real bugs (version-mismatched `pyvmomi`/`community.vmware` pairs, a module-internal `VmomiJSONEncoder` incompatibility, a `cdrom` param validation bug, `esxi_hostname`-vs-connection-`hostname` name confusion, a 10-second default upload timeout for a ~1GB file) — all symptoms of depending on that collection at all, not of this project's own code. The replacement: build everything locally (ISO, `.vmx`, SSH keys), `scp` the ISO and `.vmx` to the datastore over plain SSH, create the disk with `vmkfstools` (a local ESXi CLI tool, not an API call) over the same SSH connection, and stop there. **Registering the VM (Host Client → browse datastore → "Register VM") and powering it on are manual, by design** — that's the one step that inherently touches ESXi's inventory/management layer, and keeping it manual means the automation here never does.

`.vmx` file syntax and `vmkfstools` usage were written from general VMware documentation knowledge, not verified against a live ESXi host — there's no ESXi access in the dev sandbox. The `.vmx`'s `guestOS = "debian12-64"` is a guess (Debian 13 doesn't have its own guestOS string yet in older ESXi catalogs); `virtualHW.version = "15"` was picked as a conservative floor (supported since ESXi 6.7) to maximize compatibility — bump it if the real host supports newer.

**SSH host key is pre-generated, not left to chance**: the playbook generates a *second* keypair (`custom/generated/keys/<vm_name>_host_ed25519`, separate from `charlie`'s client keypair) and copies both halves into the ISO's injection payload; the preseed `late_command` copies them over `/etc/ssh/ssh_host_ed25519_key(.pub)`, overwriting whatever `openssh-server`'s postinst already auto-generated. This means the host key's fingerprint is known *before* the VM ever boots — no need to `ssh-keyscan` a live host and no race condition waiting for SSH to come up. Files are copied as-is (`cp /cdrom/ssh_host_key ...`), not embedded as text in `late_command` — preseed's `late_command string` is effectively one `sh -c` line, and a multi-line private key has no safe way to survive that as an inline string (no heredocs, uncertain whether `base64` is even present in the installer's minimal shell); shipping the key as a real file inside the ISO sidesteps the whole problem.

Other gotchas confirmed by direct testing in this repo's history (see git log for the specifics): `ansible.builtin.command`'s working directory is the directory *containing the playbook file*, not the directory `ansible-playbook` was invoked from — any relative path handed to a `command:` task must be absolute (`select-iso` and `build:debian` build `iso_path` with `$(pwd)/...` for exactly this reason, since Task itself reliably runs with cwd = the root `Taskfile.yaml`'s directory).

## Directory layout: official Ansible skeleton vs. `custom/`

Ansible's own documented project layout (inventory, `group_vars/`, `host_vars/`, `roles/`, top-level playbooks) only covers things Ansible itself understands — it says nothing about where project-specific tooling belongs, since that's out of Ansible's scope by design. This repo keeps that distinction explicit:

- **Repo root** — the official skeleton, plus files tools require to live at root: `inventory/`, `group_vars/`, `host_vars/`, `roles/` (all three of `group_vars/`, `host_vars/`, `roles/` are currently empty, each held by a `.gitkeep` — this project never ended up using real Ansible roles, see below, so `roles/` is reserved/unused on purpose rather than repurposed), `playbook/` (top-level playbooks, grouped by which side of the WireGuard tunnel they configure — `playbook/control-panel/debian.yml` builds the VM, `playbook/wsl/add-peer.yml` adds the control node as a WireGuard peer), `Taskfile.yaml` (by the user's preference, not an Ansible convention), `.gitignore` and `CLAUDE.md` (must stay at root for git/Claude Code to find them), and `requirements.yml` (a near-universal `ansible-galaxy` convention, kept at root).
- **`custom/`** — everything else: ISO handling (`custom/iso/`), build output (`custom/generated/`), the generated SSH keypairs (`custom/generated/keys/`), helper scripts (`custom/scripts/`), the `.env`/`.env.example` pair, `custom/preseed_iso/` (the whole Debian unattended-install source tree — see its own bullet below), and a subdirectory that used to live under `roles/*/` before a cleanup pass moved it out (see below for why): `custom/scripts/tasks/ansible/` (reusable Ansible task fragments, included via `include_tasks` with an explicit path — e.g. `custom/scripts/tasks/ansible/wireguard_keys/`, `custom/scripts/tasks/ansible/load_env/`). `custom/template/` is the other such subdirectory — Jinja2 templates rendered via `ansible.builtin.template` (e.g. `custom/template/wireguard_control_panel/`, `custom/template/wireguard_agent/`) — `custom/preseed_iso/` deliberately does **not** live under here even though it also holds `.j2` templates: it outgrew the narrow "a folder of templates" description once it started holding compiled-at-build-time shell scripts, static YAML playbooks, and JSON data alongside the templates, so it was promoted to its own top-level `custom/` entry rather than being squeezed into a category it no longer fit. None of this is Ansible-recognized; it's purely this project's own convention. `custom/scripts/tasks/` itself splits into `go-task/` (the Taskfile namespace files — `install.yaml`, `build-vm.yaml`, `verify-iso.yaml`, `windows.yaml`) and `ansible/` (the task fragments above) — same top-level folder, two different tools' files, kept apart so the name alone doesn't make you guess which kind a given file is.
- **`custom/preseed_iso/`** — the Debian unattended-install source tree, structured so the repo's own layout mirrors exactly where each file ends up on the installed VM, making "where does this land" a non-question. Three subdirectories, two of which are literal mirrors of a real VM-side path and one of which deliberately isn't: `custom/preseed_iso/template/` holds `preseed.cfg.j2` / `debian.vmx.j2` — the two root-level rendered deliverables (one becomes the injected `preseed.cfg`, the other is the hypervisor-side `.vmx`) — kept in their own subdirectory purely as a tidy work-directory home for build-time-only files, since neither is part of the VM's own filesystem tree and so neither has a real path to mirror; `custom/preseed_iso/bootstrap/` mirrors `~{{ vm_user }}/bootstrap/` on the VM (one-shot, self-deleting, tied to that one user — `services/` lives here); `custom/preseed_iso/srv/` mirrors `/srv` on the VM (persistent, server-level infrastructure that doesn't belong to any one user account — `srv/ansible/` for everything ansible-navigator/EE-related including the shared `config.sh` and `playbook/` subdir of one-shot install playbooks, `srv/harbor/` for Harbor's own bundle plus its `rotate/` day-2 update tooling, `srv/caddy/` for caddy-proxy's certs/vhost-confs, `srv/init/` for the first-real-boot one-shot system setup — `podman-network.sh`, `firewall.sh.j2`, `software-install.sh`, then `finalizer.sh`, see the Architecture section below for the systemd wiring and why this isn't tied to `{{ vm_user }}`'s own `bootstrap/` the way it used to be). `playbook/control-panel/debian.yml` stages the `bootstrap/` and `srv/` content into two parallel per-VM staging directories before remastering the ISO — `preseed_bootstrap_output_dir` and `preseed_srv_output_dir` — each one also mirroring the same final on-VM structure, so `preseed.cfg.j2`'s `late_command` can inject each tree with a single recursive `cp -r` instead of one `cp`/`chmod` line per file.

**Why the `roles/*/` content moved out**: it was never actually using Ansible's role mechanism to begin with — real roles can't declare their own `hosts:` (that's a play's job), and this project's `include_tasks`/`template` calls always spelled out the full explicit path (`{{ playbook_dir }}/../../roles/...`) rather than relying on `include_role`'s automatic role-relative path resolution, because `include_role`'s search path only checks `roles/` relative to the *playbook's own directory*, which this project's `playbook/control-panel/roles/` never had (confirmed by direct testing — see the WireGuard section below). So the `roles/` directory name was borrowed purely for familiarity, while every file in it was in practice just a plain task-fragment/template file reached by hardcoded path — indistinguishable, mechanically, from anything living under `custom/`. Once that was pointed out, the content moved to where it actually semantically belongs (`custom/`), and `roles/` went back to being an unused, reserved part of the official skeleton, matching `group_vars/`/`host_vars/`.

## Commands

- `task --list` — list available tasks
- `task install` — install local tooling; runs `install:default` from the included `install` namespace: `install:ansible` (ansible-core + collections from `requirements.yml`), `install:iso-tools` (`xorriso`, `isolinux`), `install:gum`, `install:jq`, `install:sshpass` (needed so `build:debian` can SSH into the hypervisor non-interactively via `SSHPASS`), `install:wireguard-tools` (`wg`/`wg-quick`, needed locally to generate WireGuard keys — WireGuard is a mandatory part of every build, not optional, so this is needed on every machine that runs `build:debian`)
- `task select-iso` — interactively pick an OS registered in `custom/iso/manifest.json` (via `gum choose`), prints the resolved ISO path; fails if the file isn't actually present under `custom/iso/`
- `task verify-iso` — interactively pick an OS, verify its registered ISO is an unmodified official release
- `task build:debian` — `gum confirm`s whether to add *this* machine as a WireGuard peer of the VM being built (runs `playbook/wsl/add-peer.yml` first if so — see the WireGuard section below; declining this just means no machine is enrolled as a peer yet, not that the VM skips WireGuard — it never does), `gum confirm`s before repackaging an already-existing local ISO and before overwriting an already-existing remote datastore folder, sources `custom/.env`, looks up `manifest.json`'s `debian` entry (`iso-path` + `build-path`), runs `ansible-playbook <build-path>` with the resolved ISO path. Produces and uploads everything; does **not** register or power on the VM — the task's final `debug` output tells you what to do manually, including the exact `known_hosts` line to add once you know the VM's IP.

## Architecture

- `Taskfile.yaml` — root task definitions; includes namespaced task files from `custom/scripts/tasks/go-task/` (`install.yaml` as `install`, `build-vm.yaml` as `build`, `verify-iso.yaml` as `verify-iso`, `windows.yaml` as `windows`). Add new task groups the same way rather than growing the root file.
- `custom/iso/manifest.json` — maps an OS name to `{"iso-path": "<path under custom/iso/>", "build-path": "<playbook path>"}`. Single source of truth for both `select-iso`/`verify-iso` (only need `iso-path`) and `build:*` (needs both, to know which playbook to run without any task hardcoding a filename).
- `custom/iso/` — holds *source* ISO files. Scoped `.gitignore` (ignore everything except `manifest.json` and itself); place actual ISO files here manually, e.g. `custom/iso/debian/<filename>` matching the registered `iso-path`.
- `custom/scripts/verify-iso/debian.sh` — verifies a Debian ISO is an unmodified official release, entirely at run time with no long-lived trust material committed to the repo: `read`-prompts for the mirror directory (default `current`, which also doubles as a "new release available" signal if the ISO's filename no longer matches what that directory serves), downloads the three Debian CD signing keys fresh from `debian.org/CD/key-<id>.txt`, checks their fingerprints against constants pinned in the script, cross-checks those pinned constants against what `debian.org/CD/verify` currently publishes (hard-fails on any mismatch), then `gpgv`-verifies the signature and `sha512sum -c`s the ISO. Usage: `debian.sh <path/to/iso>`. Verified end-to-end against the real Debian 13.7.0 netinst ISO — not a "hasn't been tested" caveat like some other scripts here.
- `custom/generated/` — build output, split by role and namespaced per VM name (so building multiple VMs doesn't have them overwrite each other's files): `custom/generated/preseed/<vm_name>/` holds `preseed.cfg` plus copies of the pre-generated host-key files (the full *injection payload* that gets copied into the ISO — an intermediate input, not a deliverable itself); `custom/generated/iso/<vm_name>/` holds the actual deliverables, the repacked ISO and the rendered `.vmx`.
- `playbook/control-panel/debian.yml` — the main entry point for building the VM (named "control-panel" because this VM is also the WireGuard server — see the WireGuard section below). Runs entirely against `localhost`. Flow: generate the `charlie` client keypair and a separate VM host keypair under `custom/generated/keys/` → copy both host-key files into `custom/generated/preseed/<vm_name>/` → render `preseed.cfg` there → remaster the ISO via `custom/scripts/remaster-iso/debian.sh` into `custom/generated/iso/<vm_name>/` → render `debian.vmx` into the same dir → SSH into the hypervisor to `mkdir` `/vmfs/volumes/<datastore>/<vm_name>/`, `scp` the ISO and `.vmx` there, and run `vmkfstools` there to create the disk (`<vm_name>.vmdk`) — the `.vmx`'s disk/cdrom references are bare filenames, not full paths, relying on all three files sitting in that same remote folder together. Ends there; see "Project status" above for why registration/power-on aren't automated.
- `custom/scripts/remaster-iso/debian.sh` — now takes `<source.iso> <extra_files_dir> <output.iso>` (previously just a single `preseed.cfg` path) — everything in `extra_files_dir` gets copied to the repacked ISO's root, since there are now multiple files to inject (`preseed.cfg`, `ssh_host_key`, `ssh_host_key.pub`). Extracts read-only via `xorriso -osirrox` (no `mount`/`sudo`/loop device). Boot automation needs two layers: (1) add the preseed kernel args to the menu entry that's actually auto-selected — BIOS: `isolinux/gtk.cfg`'s `installgui` (has the real `menu default` flag; `isolinux/txt.cfg`'s `install` is just the text-mode fallback, patch both to be safe) and UEFI: only the *first* `menuentry` in `boot/grub/grub.cfg` (that file has ~19 matching kernel lines across rescue/speech/dark-theme variants — don't patch all of them); (2) force a short menu timeout, since the defaults mean *wait forever for a keypress* (isolinux's `timeout 0` is a special "disabled" value, not "0 seconds"; grub has no timeout/default set at all). Repacks with `xorriso`, using `/usr/lib/ISOLINUX/isohdpfx.bin` from the system's `isolinux` package for the isohybrid MBR — that file does not exist inside the source ISO itself.
- `custom/preseed_iso/template/preseed.cfg.j2` / `debian.vmx.j2` — the two Jinja2 templates rendered by `playbook/control-panel/debian.yml`. See the `custom/preseed_iso/` bullet above for the rest of that tree.
- `custom/preseed_iso/srv/init/` — first-real-boot, one-shot system setup, VM-side path `/srv/init/`. Four files, run in a fixed order via four systemd units that `late_command` writes inline (same `echo >> /target/etc/systemd/system/<name>.service` style as the WireGuard/SSH unit below), each gated by `ConditionPathExists=` pointing at the script's own path (not `ConditionFirstBoot=yes` — a stale comment in an earlier version of this file claimed that, but the actual mechanism has always been the path check), chained with `After=`/`Requires=` on the previous unit:
  1. `podman-network.sh` (plain script, no Jinja — the two values it needs, the subnet and gateway, are fixed project constants, not something that varies per VM) — idempotently (`podman network exists` check first) creates a dedicated podman network (`ansible-builder-network`, pinned to `10.90.0.0/24` with `--gateway 10.90.0.1`, pinned explicitly for the same reason the subnet itself is — not left to podman's "pick the first usable address" default, since `firewall.sh.j2`'s `ufw` rule and `config.sh`'s `http_proxy` both need to know this value and an implicit default could silently change on a podman upgrade) used for exactly one thing: the `podman build` step in `config.sh`'s `ensure_ee_image()` needs outbound access (`apt-get`/`pip` installing packages into the EE image), and that build runs as root through a real bridge network, unlike every other podman usage on this VM — `ansible-navigator` itself runs the EE container with `--network=host` (see `ansible-navigator.yml`), and the rootless `harbor`/`caddy-proxy` users default to `slirp4netns`/`pasta` instead of a bridge — so this is the *only* podman network on the whole VM that ever needs any firewall attention at all.
     `podman network create` only writes the network's *config*; podman's netavark backend doesn't actually plumb the bridge device and gateway IP onto a host interface until the first container attached to that network actually starts (CNI, podman's older backend, has the same lazy-provisioning design — not a netavark-specific quirk). This was a real rabbit hole: an earlier version had `squid.sh` (below) bind specifically to `10.90.0.1` as extra defense in depth, which broke on actual hardware because that address genuinely doesn't exist on any interface until `ensure_ee_image()`'s `podman build` runs (the first real container this VM ever attaches to this network) — and `squid.sh` runs *before* that. Three increasingly elaborate fixes were explored (a throwaway pod to force the bridge into existence early, created-started-then-removed; a statically-configured OS-level bridge via systemd-networkd; a global `net.ipv4.ip_nonlocal_bind = 1` sysctl) before landing on the actual fix: don't bind to that address at all. `10.90.0.1` is podman's own internal routing concern for letting containers reach the host — nothing about squid or the OS needed to anchor itself to it specifically, and doing so bought zero additional security (the real access-control boundary was always the two independent layers below: `firewall.sh.j2`'s `ufw` rule matching the packet's *destination* address, and `squid.conf`'s own `acl localnet` matching its *source* — neither cares what interface squid's listening socket happens to be bound to). So this script only needs the network's *config* to exist, never the gateway IP's actual on-the-wire appearance — the timing question that drove three rounds of increasingly fragile workarounds turned out not to matter at all once the unnecessary bind was removed.
  2. `firewall.sh.j2` (renamed from the old `custom/preseed_iso/bootstrap/bootstrap-firewall.sh.j2` — moved out of `bootstrap/` into `srv/` because it isn't actually tied to `{{ vm_user }}`'s login/bootstrap flow, it's server-level init wired through its own independent systemd unit) — applies the same `ufw` rules that `late_command` can't apply reliably itself (see below for why), plus one rule for the `ansible-builder-network` network: `ufw allow from 10.90.0.0/24 to 10.90.0.1 port 3128 proto tcp`. This is a plain `allow` (INPUT chain), not `ufw route allow` (FORWARD chain) — the build container's only destination is the host itself (`bootstrap/services/squid.sh`'s forward proxy, listening on the network's own gateway address), not the open internet, so nothing is ever actually *forwarded*; the once-live `DEFAULT_FORWARD_POLICY=DROP` problem this project hit early on (ufw's default blocks bridge-forwarded traffic) is no longer relevant to this network at all, by construction, not by an exception to it. An earlier version of this rule set *did* need `ufw route allow` (the build container talked straight to the internet: DNS to two pinned resolvers, HTTPS to `any` on port 443) and that version's "narrow the blanket `to any`" discussion is what led to inserting squid as a real domain-level whitelist instead of trying to get an IP-based rule to do a job it structurally can't (CDN IPs for package mirrors aren't fixed, so "narrow by IP" always degrades to "open port 443 to everywhere").
  3. `software-install.sh` — installs `task` (go-task) and `gum` into `/usr/local/bin`, system-wide, plus `ansible-navigator` via `pipx install --global` — all three were previously missing from `pkgsel/include`/the hand-written `Containerfile` package lists and needed in a place every user could reach, not stashed in one user's `~/.local/bin`. Moved here from `late_command` after a real hardware failure: `late_command`'s `in-target pipx install ansible-navigator` looked fine (no error surfaced during install) but the binary simply never existed after boot — same root cause as the rest of this section's `in-target`/d-i-chroot skepticism (`pipx install` needs a real network connection and a stable `$HOME`, neither guaranteed inside the minimal d-i environment `late_command` runs in). Confirmed by a real `bootstrap-services` run failing with "找不到 ansible-navigator". The script itself runs rootless (`software-install.service`'s `User=`/`Group={{ vm_user }}`) — it only does the parts that touch untrusted downloaded content (curl/`sha256sum -c`/`tar` for task and gum, into a staging directory), never writing to `/usr/local/bin` directly. That directory (and `/opt/pipx`, `pipx install --global`'s target) deliberately keep their normal `root:root` ownership — an earlier draft of this fix `chown`'d both to `{{ vm_user }}` so the whole script could stay root-free, but that was rejected as too broad a permissions change for what should be a narrow, one-off install step. Instead, the *placement* into those root-owned paths happens via three more `ExecStart=` lines on the same unit, each prefixed with systemd's `+` (which makes that one line run with full privileges regardless of the unit's `User=`/`Group=` and sandboxing settings — a feature that exists specifically for this "mostly-unprivileged service, one privileged cleanup/install step" shape): `+/usr/bin/mv .../task /usr/local/bin/task`, the equivalent for `gum`, and `+/usr/bin/pipx install --global ansible-navigator` (pipx has no own root requirement — `--global`'s default target directories being root-owned is the only reason this one needs the `+`). The staging directory itself is `RuntimeDirectory=software-install` (`/run/software-install`, auto-created by systemd with `User=`/`Group=` ownership before any `ExecStart=` line runs) rather than a hand-rolled `mktemp`, specifically so its path (`${RUNTIME_DIRECTORY}`, a real systemd command-line expansion, not shell syntax — works in every `ExecStart=` line on the unit, `+`-prefixed or not) only has to be written once, as the `RuntimeDirectory=` value, instead of being duplicated between the script and the unit's later `mv` lines where a mismatch could silently break the install. A final `+rm -rf ${RUNTIME_DIRECTORY}` line cleans it up (not strictly required — `/run` is tmpfs and gets wiped on reboot either way — but kept for the same explicit-cleanup discipline `finalizer.sh` already follows). Idempotent via `command -v` checks for `task`/`gum` inside the script; `pipx install --global` re-running against an already-installed package is harmless on its own.
  4. `finalizer.sh` — the only one of the four that deletes anything, and the only reason this is four scripts instead of one: cleanup (`rm -rf /srv/init`, deleting itself along with everything else — same "delete a file that's still executing" trick the old single-script version used, just now at directory scope) is kept out of the other three scripts on purpose, so each one's own exit code only ever reflects whether *its own* job succeeded, not an unrelated `rm`. `finalizer.service` has `After=`/`Requires=software-install.service`, which itself `Requires=firewall.service`, which itself `Requires=podman-network.service` — so `finalizer.service` only ever actually runs once all three earlier units are `active`. If any of them fails, this one never runs, and `/srv/init/` (all four files) stays in place for a retry.
- `custom/preseed_iso/bootstrap/services/squid.sh` — configures the actual forward proxy the `ansible-builder-network` network's `ufw` rule (above) exists for: Squid (the package installed via `preseed.cfg.j2`'s `pkgsel/include` is **`squid-openssl`**, not plain `squid` — Debian/Ubuntu's default `squid` package is built against GnuTLS, not OpenSSL, for licensing reasons, and ssl-bump's `http_port` options rely on OpenSSL-specific APIs that build doesn't have, so a plain `squid` install would fail at `squid -k parse`/startup; the two packages provide/conflict on the same files and can't coexist, but both still produce a binary named `squid`, so this script's `command -v squid` check and the rest of its logic don't need to know which variant is installed — same reasoning as the rest of this paragraph for why installation itself stays out of this script, not `apt-get install`ed at runtime, for the same "`late_command`'s `in-target` calls silently misbehave inside d-i's own chroot" reason `ufw enable` itself can't live in `late_command`; this script only checks the binary exists and errors out otherwise, mirroring `config.sh`'s `ensure_navigator_tools()`), in **full TLS bump** mode (every `CONNECT` is decrypted and re-signed with a locally-generated CA, not just peeked at for SNI) so the whitelist in `/etc/squid/allowed_domains.txt` is matched against the real decrypted `Host`, not a value the client could lie about (a plain `CONNECT`-host or SNI-only check can be spoofed — the client declares one target and negotiates TLS to another; closing that gap is why this project chose full bump over the cheaper SNI-`peek`-and-`splice` middle ground, accepting the one extra cost: a CA now has to be trusted inside the EE build container). `http_port` deliberately does **not** bind to a specific address — it listens on all interfaces, relying entirely on `squid.conf`'s own `acl localnet` / `http_access deny !localnet` for the source restriction and the `ufw` rule above for the destination/port restriction. An earlier version bound specifically to `10.90.0.1` (the `ansible-builder-network` gateway) as extra defense in depth and broke on real hardware for exactly the reason explained in `podman-network.sh`'s entry above — see that for the full story of why this was reverted rather than patched around. `acl localnet` matches both `10.90.0.0/24` (the build container, via the bridge) *and* `127.0.0.1/32` (the host itself) — listening on all interfaces already covers loopback for free, so no second `http_port` line was needed, just the broader source ACL. The host-side path exists because `config.sh`'s `ensure_ee_image()` (below) now routes its own `podman pull` of the EE's base image through this same squid rather than letting it bypass the whitelist by going straight to the internet — this script copies its CA into `/usr/local/share/ca-certificates/` and runs `update-ca-certificates` so the host's own TLS client (podman/skopeo, reading the system trust store same as everywhere else `update-ca-certificates` is used in this project, e.g. `harbor.sh`'s `LOCAL_CA_TRUST_PATH`) accepts the full-bump-resigned connection. Uses `tls-cert=`/`tls-key=` (not the older `cert=`/`key=`, deprecated — kept only as compatibility aliases — since Squid 5) — worth checking `squid -k parse`'s output for deprecation warnings the first time this actually runs on real hardware, since the exact `squid-openssl` version on trixie hasn't been checked in this dev sandbox. The domain whitelist is a separate, plain-text file *by design* — "any domain can just be added to it" (the user's framing) without touching `squid.conf` or a restart (`systemctl reload squid` picks up edits); its seed list (`.docker.io`, `.docker.com`, `.debian.org`, `.pypi.org`, `.files.pythonhosted.org`) maps directly to the `Containerfile`'s own `FROM debian:13-slim` (Docker Hub, both the registry API domain and the Cloudflare-backed CDN that actually serves image layers), `apt-get` (Debian's own mirrors), and `pip install ansible-core` (PyPI) — not guesses at what some third-party base image's package manager might reach, but a direct reading of the two `RUN` lines in this project's own hand-written `Containerfile`. Still **not verified against a real build** — same honesty caveat as the `.vmx` `guestOS` string elsewhere in this doc; a denied domain shows up as `TCP_DENIED` in `/var/log/squid/access.log` and just needs appending to the file. Two things worth calling out since they look like they'd need more infrastructure than they do: the dynamic-certificate cache at `/var/lib/squid/ssl_db` is capped at 4MB (`-M 4MB`) — nowhere near Harbor's registry-blob scale, so it stays on the root filesystem, no dedicated disk; and the `chown proxy:proxy` on the CA files isn't this script inventing a user — `proxy` (UID/GID 13) is one of Debian's `base-passwd` reserved system accounts, present on every Debian install including a minimal one, and it's simply the account Squid's own packaged default (`cache_effective_user`) already runs as. Deliberately lives in `bootstrap/services/` (the interactive, one-shot `bootstrap-services` flow — same home as `harbor.sh`/`nginx.sh`), not `srv/init/`: its only consumer, `ensure_ee_image()`, is itself only ever invoked from that same interactive flow, so there's no benefit to making squid come up any earlier than bootstrap-services does, and by the time bootstrap-services runs (a human has to SSH in and fill out a form) `srv/init/`'s four units have always long since finished, so the `ansible-builder-network` network and its gateway address already exist.
  Also updated alongside this: `config.sh`'s `ensure_ee_image()` now calls plain `podman build --network ansible-builder-network --build-arg http_proxy=http://10.90.0.1:3128 --build-arg https_proxy=http://10.90.0.1:3128 -f Containerfile -t "$EE_IMAGE" /etc/squid/ssl_cert` — `--network ansible-builder-network` puts the build container on the network the firewall rule above expects; the build context is `/etc/squid/ssl_cert` (not `$EE_DIR`) specifically so the Containerfile's `COPY squidCA.crt ...` line can read it. The previous `--dns=1.1.1.1 --dns=8.8.8.8` flags are gone — the build container no longer resolves any external name itself, it only ever connects to the fixed IP `10.90.0.1`.
- `ansible-navigator.yml`'s `container-options` includes `--user=0`, added after a real multi-round debugging session on actual hardware. Without it, the EE container runs as whatever default UID the base image ships (many Ansible EE images default to a non-root numeric UID for OpenShift arbitrary-UID compatibility) — and because this same config bind-mounts the host's entire `/etc` into the container, that numeric UID resolves to *whatever host account happens to own it*, not to any identity this project controls. On the actual VM this was `charlie` (host UID 1000), so `rootless_podman_user_setup.yml`'s `become_user: harbor` task was unknowingly running as `charlie` instead of root, and then failing when charlie (correctly) wasn't able to sudo without a password. `--privileged` already grants the container's process full Linux capabilities regardless of its nominal UID (so this collision never broke the `useradd`/filesystem-mutating tasks that happen *without* `become`), but `sudo`'s own identity check for "is the caller already privileged enough to skip authentication" cares about the nominal UID specifically — hence this only ever surfaced on the one task that uses `become`.
  Fixing the UID didn't fully fix the underlying problem, though: even as genuine root (confirmed via `id` showing `uid=0`), `sudo -n -u harbor ...` still failed with `PAM account management error: Permission denied` / `sudo: a password is required`. The actual cause, found by reading `/etc/sudoers` directly: this Debian-based image's PAM stack (`/etc/pam.d/sudo` → `common-auth`/`common-account`) doesn't include `pam_rootok.so` the way RHEL-family `system-auth` configs typically do, and `/etc/sudoers`' own `root ALL=(ALL:ALL) ALL` entry has no `NOPASSWD` tag — so on this distro, *even real root* is not exempt from sudo's authentication requirement by default. This is distinct from (and more fundamental than) the UID-collision bug above; fixing one without the other still fails. The actual fix: `preseed.cfg.j2`'s `late_command` writes a narrowly-scoped `/etc/sudoers.d/ansible-ee-rootless-become` — `root ALL=(harbor,caddy-proxy) NOPASSWD: ALL` — granting NOPASSWD only for root becoming one of these two specific rootless service accounts, not a blanket NOPASSWD grant for root in general (which it doesn't need; it already has `ALL`, just gated behind authentication). Confirmed working by hand on the actual VM before being written back into this file: `sudo -n -u harbor podman info` went from the PAM/password error straight through to a real (unrelated) rootless-podman runtime error, confirming the sudo layer itself was the entire blocker.
  **This EE image is no longer built via `ansible-builder` at all — `execution-environment.yml` is gone, replaced by a hand-written `custom/preseed_iso/srv/ansible/Containerfile` built with a plain `podman build`.** `ansible-builder` was the original choice (generates a Containerfile from a declarative YAML, which is all this project ever needed it for — nothing here depends on AWX/AAP-specific metadata), but it turned out to have a hard, undocumented-until-you-hit-it constraint: it's intentionally RHEL-only. Confirmed directly from the maintainers, not inferred: GitHub issue ansible/ansible-builder#636 quotes a maintainer saying "Not really a bug since builder is intentionally designed to work only with RHEL'ish images," and the official docs state plainly that "non-RPM package managers such as apt-get (Debian/Ubuntu) ... are not supported and will cause build failures." This project's VM is Debian, so the EE image (`quay.io/ansible/creator-ee`, the RHEL/Fedora-based default `ansible-builder` examples point at) was the *only* non-Debian thing in the whole stack — and it caused a real, multi-round debugging session: `ansible-navigator.yml` bind-mounts the host's entire `/etc` into the EE container (needed so `useradd`/`/etc/subuid` edits/etc. land on real VM state), and Debian's `/etc/pam.d/sudo` (`@include common-auth`/`common-account`) being read by the *image's own* Fedora-native `sudo`/libpam broke PAM's account phase unconditionally — confirmed by testing `sudo -n -u root id` (switching to yourself, root to root, needing zero authentication) and watching it fail identically to `become_user: harbor`, then re-running the exact same command with no `/etc` mount at all (pure native Fedora environment) and watching PAM succeed. The mismatch was never about *which* user; it was two different distros' PAM conventions colliding the moment the bind-mount merged them. `quay.io/ansible/creator-ee` is also archived/unmaintained (its GitHub repo says container building "moved inside ansible-dev-tools projects"); its documented successor, `ghcr.io/ansible/community-ansible-dev-tools`, is *also* Fedora-based, so migrating to it wouldn't have fixed anything here. The fix: stop using `ansible-builder` and its RHEL-only base images altogether. `Containerfile` is `FROM debian:13-slim` — same distro as the VM host, so the `/etc` bind-mount is now same-distro-to-same-distro and this entire class of mismatch can't recur (CA paths, `nsswitch.conf`, `os-release`, `/etc/alternatives` — none of it needs separate handling anymore, because there's no longer a second distro's conventions to collide with). It installs `python3`/`python3-venv`/`podman`/`passwd`/`sudo` via `apt-get`, then installs `ansible-core` via `pip` into a dedicated venv (same reasoning as `pipx`-installing `ansible-navigator` on the host: pin the version explicitly, don't inherit whatever Debian's own package happens to carry). Being a single, hand-written stage also means Squid's CA only needs trusting once (`COPY squidCA.crt ...` + `update-ca-certificates`, right after `FROM`) — the entire multi-stage CA-trust saga this section used to describe (a `localhost/creator-ee-squid-trusted:latest` derived image, `prepend_builder`/`append_base` hooks racing an internal `pip install bindep pyyaml packaging` step that always won) no longer applies, because there's only one stage and this project wrote every line of it.
  `http_proxy`/`https_proxy` are still passed as `--build-arg`, not exported as env vars on the `podman build` process itself, for the same reason as before: the outer process's env vars are visible to podman/skopeo's own registry-pull code (standard Go `net/http` behavior, independent of `podman build`'s `--http-proxy` flag), so exporting them risks leaking the proxy into a step that was never meant to use it. It matters less now (the base image is pre-pulled, see below, so `FROM` never touches the network either way) but keeping the discipline costs nothing.
  The base image (`debian:13-slim`) is still pre-pulled by `ensure_ee_image()` itself, *before* calling `podman build`, using `https_proxy="http://127.0.0.1:3128"` (not `10.90.0.1` — this pull is the host's own process talking to itself over loopback, not a build container talking to its bridge gateway) through the same squid (which already listens on all interfaces, loopback included, and whose `acl localnet` explicitly covers `127.0.0.1/32` alongside `10.90.0.0/24`; `squid.sh` also makes the host trust squid's CA so this pull's full-bump-resigned TLS doesn't fail validation) — the goal is still "every outbound connection this VM makes gets audited by squid's whitelist, including the host's own," not just the build container's. This hardcodes the base image name a second time (keep it in sync with the `FROM` line in `Containerfile`) — an accepted, acknowledged duplication, not an oversight, same as the subnet/gateway values duplicated across `podman-network.sh`/`firewall.sh.j2`.
- **`harbor-install.yml`'s full run, end to end on real hardware, surfaced a long chain of real bugs — all confirmed by repeatedly tearing down the `harbor` account (`userdel -r -f` + scrub `/etc/subuid`/`/etc/subgid`) and re-running `apply.sh` from a genuinely clean state, not by patching around a one-off error.** In rough chronological order:
  - `ansible.builtin.user`'s `create_home: true` (i.e. `useradd -m`) only `chown`s the home directory to the new owner *if the path doesn't already exist* — if `/home/harbor` was ever left behind by an earlier account (deleted without `-r`, or touched before the account existed), `useradd` leaves its ownership untouched. Hit this directly: `/home/harbor` sitting at `root:root` meant `harbor` couldn't write anywhere under its own home — not `.ansible/tmp`, not `.local`, not `.config` — surfacing as `Permission denied` on whatever the first write happened to be. Fix: `rootless_podman_user_setup.yml` now has an explicit `ansible.builtin.file` task right after user creation that unconditionally re-asserts ownership of the home directory, regardless of what state it started in.
  - `newuidmap`/`newgidmap` (the setuid-root helpers rootless podman needs to actually apply the `/etc/subuid`/`/etc/subgid` multi-ID mappings) are not part of the `podman` package at all — they're in the separate `uidmap` package, which `preseed.cfg.j2`'s `pkgsel/include` didn't have and the hand-written `Containerfile` didn't have either. Missing it surfaces as `command required for rootless mode with multiple IDs: exec: "newuidmap": executable file not found in $PATH`. Added to both package lists.
  - The actual root cause of the mystery that ate the most debugging time — `become_user: harbor`'s *first-ever* `podman` invocation inside a given `ansible-navigator` run reliably failing with either `mkdir /run/user/<uid>/libpod: permission denied` or `getting available cgroup controllers: ... podman-<pid>.scope: no such file or directory`, while the exact same command retried a few seconds later (in a *fresh* container) succeeded immediately — turned out to be a mount-propagation problem, not a permissions or cgroup problem. `ansible-navigator` runs one single long-lived EE container for the whole playbook; that container starts *before* the `harbor` account (and therefore before `/run/user/<uid>`, the tmpfs `systemd-logind` mounts the moment `loginctl enable-linger` runs) exists. `ansible-navigator.yml`'s `/run` volume-mount is a plain bind (`options: rw`), which podman defaults to `private` propagation — a mount created on the host *after* the container started never becomes visible inside it. A brand-new container (my own manual `podman run` during debugging) started *after* `/run/user/<uid>` already existed got a correct initial snapshot and worked every time, which is exactly the "retry in a fresh container succeeds" pattern that pointed at propagation rather than permissions. Fix: the `/run` mount moved out of the structured `volume-mounts` list (whose `options:` field is whitelist-validated by `ansible-navigator` itself to `ro`/`rw`/`Z`/`z`/`O` — passing `rslave` there is rejected outright with `Unrecognized option: 'rslave'` before it ever reaches podman) into `container-options` as a raw `-v /run:/run:rw,rslave`, which `ansible-navigator` forwards to podman verbatim with no validation. `rslave` (not the fully bidirectional `rshared`) is enough: the container only needs to *receive* new mounts the host creates later, never needs to propagate its own mounts back out.
  - Once that was fixed, `podman info`/`podman ps` specifically — as opposed to `podman pull`/`podman run`, which both worked fine under the identical `become_user` call — kept failing with the same cgroup-controller/`libpod`-directory errors in a way that turned out to be a real, narrow limitation of those two subcommands' own diagnostic/self-placement logic when invoked via a plain `sudo -u`/`become_user` switch that never went through a real PAM-session-registering login (confirmed by cross-testing `podman info` against `podman ps`/`pull`/`run` side by side, repeatedly, under identical environment and identical retries). The playbook's own health-check task now runs `podman ps`, not `podman info` — `ps` actually talks to podman's API socket (i.e. proves rootless podman works), where `info`'s failure here says nothing about whether the rest of the pipeline will work.
  - `goharbor/prepare` (itself a container, started by `harbor`'s own rootless podman) failed with `crun: create directory \`/sys/fs/cgroup/.../user.slice\`: No such file or directory` — a *second*, independent cgroup problem, this time because `harbor` is a genuine rootless, non-privileged account with no real host-level capability to join the host's cgroup namespace; the default `systemd` cgroup manager assumes exactly that capability to create a delegated `podman-<pid>.scope`. Setting `cgroup_manager = "cgroupfs"` in `harbor`'s (and `caddy-proxy`'s) own `~/.config/containers/containers.conf` sidesteps the whole assumption — crun just operates directly on whatever cgroup filesystem it can actually see, instead of demanding a systemd-delegated path it has no permission to create. Written once per rootless user in `rootless_podman_user_setup.yml`, so it applies to every later `podman run` that user makes, including the ones `podman-compose` issues internally when it eventually brings Harbor's own services up — not just this one `prepare` call.
  - `podman pull`/`podman run`, when invoked through `become_user` *inside the EE container*, separately failed trying to create a temp dir under `/var/tmp` (`creating a temporary directory: mkdir /var/tmp/container_images_storage...: no such file or directory`) — even though a plain `mkdir` at that exact path, by that exact user, in that exact container, worked fine. `/var/tmp` inside the EE container is just the image's own local filesystem (never bind-mounted from the host, unlike `/etc`/`/home/<user>`/`/srv`/`/var/lib`/`/var/cache`), and podman's internal multi-UID storage-handling re-exec apparently can't reliably use it there. Fix: `rootless_podman_user_setup.yml` sets `TMPDIR` (in the shared `rootless_podman_env` fact) to a directory under the rootless user's own home instead — a path that *is* bind-mounted from the host, so it's unambiguously real and writable.
  - `ansible-navigator.yml`'s `volume-mounts` never included `/srv` at all. `harbor_home`/`caddy_proxy_home` (`/srv/harbor`, `/srv/caddy`) are both under it, and anything the EE container does with files there (e.g. the task that tightens `harbor.yml`'s permissions) sees the path as simply absent — the file genuinely exists on the host, just not inside the container's mount namespace. Fixed by mounting all of `/srv` (matching the existing "mount broad top-level directories wholesale" pattern already used for `/etc`/`/var/lib`/`/var/cache`, rather than enumerating every subdirectory a given playbook happens to touch today).
  - A cluster of packages turned out to be missing from the hand-written `Containerfile` purely because they're `Recommends`, not `Depends`, of packages already being installed — the host's own `pkgsel/include` pulls `apt`'s Recommends by default so it never noticed, but the Containerfile's `apt-get install --no-install-recommends` (deliberately scoped so the package list stays an explicit, intentional set — see the `Containerfile`'s own comments) skips them. All confirmed by the exact failure each produced, not guessed: `passt`/`slirp4netns` (rootless container networking — `could not find pasta ...`), `nftables` (netavark's NAT/forwarding rules for the podman-compose project's internal network — `netavark: nftables error: unable to execute nft`), `aardvark-dns` (inter-container DNS by name within that same network). All four are now explicit lines in the Containerfile.
  - `yq` was a different kind of bug entirely: `apt install yq` on Debian gets `kislyuk/yq` — a Python wrapper around `jq` with jq's own CLI conventions — but `harbor-install.yml`'s `yq -i 'del(.services.log) | ...'` calls are written in `mikefarah/yq` v4's native-YAML-path syntax, a completely different, API-incompatible tool that happens to share a binary name. The two can't be told apart by "is yq installed" — only by actually running the command (`yq: -i/--in-place can only be used with -y/-Y/-t/-x` is kislyuk's yq rejecting mikefarah's syntax). Fix: stopped installing the apt `yq` package anywhere (checked — nothing on the host itself ever actually calls `yq`; only `harbor-install.yml`, which only ever runs inside the EE container, does), and the `Containerfile` now downloads `mikefarah/yq`'s static Go binary directly from its GitHub release (pinned version, not `latest`, for the same reproducibility reason other versions in this project are pinned) — which also meant adding `curl` to the Containerfile and `.github.com`/`.githubusercontent.com` to squid's domain whitelist (the release page and the actual asset-serving CDN are different domains).
  - `podman-compose` itself was also simply missing from the `Containerfile` — it's a separate Debian package from `podman`, not pulled in by it at all, apt-Recommends or otherwise. Added explicitly.
  - Two more bugs were in `harbor-install.yml`'s own logic, unrelated to the environment: a task used `ansible.builtin.command: command -v podman-compose` to resolve an absolute path for a systemd unit's `ExecStart=` — but `ansible.builtin.command` execs its argument directly with no shell involved at all, and `command -v` is a shell *builtin*, not a file that exists anywhere on disk to be exec'd, so it fails immediately with an opaque, contentless `rc: 2`. Switched to `which podman-compose`, a real binary. Separately, the playbook's very last two tasks were in the wrong order — "delete the one-time `harbor_runtime_vars.yml`/`harbor-install.yml` files" ran *before* "print a summary that references `{{ harbor_hostname }}`," a variable that file's own `vars_files:` had supplied — so the final debug task failed with `'harbor_hostname' is undefined` after literally everything else had already succeeded. Swapped the order.
- Secrets (hypervisor hostname/credentials/datastore/network) live in `custom/.env`, gitignored; `custom/.env.example` documents the required `HYPERVISOR_*` keys (named generically, not `ESXI_*`, since nothing here is actually ESXi-API-specific anymore — swapping to a different SSH-reachable hypervisor would mainly mean writing a different `.vmx`-equivalent template) and is the tracked template. The playbook reads these via `lookup('env', ...)`; `build:debian` sources `.env` before invoking `ansible-playbook`. Treat `custom/.env` as off-limits to read directly once the user has filled it in with real values — ask them to confirm things themselves instead.
- SSH to the hypervisor uses `sshpass -e` (password via the `SSHPASS` env var, set per-task via Ansible's `environment:`, never passed as a literal `-p` argument) — deliberately chosen over setting up SSH keys for the hypervisor connection, after discussing the risk (password briefly visible to other local processes/users via `ps`/`/proc` during the connection — low-severity on a single-user control node, which this project already assumes given `.env` holds plaintext secrets regardless).
- SSH key handling: both the `charlie` client keypair and the VM's host keypair are generated locally (`community.crypto.openssh_keypair`, under `custom/generated/keys/`). Only public halves + the full host keypair get baked into the ISO; client *private* keys never leave the control node and are never committed.

## WireGuard (mandatory, not optional)

Every `debian-vm` build is a WireGuard server — there is no toggle for this, no `enable_wireguard`-style variable anywhere, and no way to build the VM without it. This was a deliberate correction: an earlier version of this feature gated the whole thing behind an `enable_wireguard` extra-var, and the user explicitly rejected that framing — WireGuard is a hard requirement of every build, full stop. The VM (`playbook/control-panel/debian.yml`) is named "control-panel" specifically because it's also the WireGuard **server**; the control node running `ansible-playbook` (in practice, the user's WSL2 machine) can be enrolled as a **peer** via `playbook/wsl/add-peer.yml`.

The *only* thing that's actually optional is whether the current machine gets enrolled as a peer in any given `build:debian` run — `custom/scripts/tasks/go-task/build-vm.yaml`'s `gum confirm` asks exactly that, nothing more. Declining it does not disable WireGuard on the VM; it just means no peer gets added this run (the VM still comes up as a WireGuard server with a pre-generated, as-yet-unclaimed peer slot — see below). The file is named `add-peer.yml`, not `agent.yml`, on purpose: being added as a WireGuard peer doesn't imply this machine becomes a cluster "agent" node of anything (there's no cluster — no k3s or similar has been set up in this project at all) — it was named that way once and renamed after the user pointed out the misleading implication.

- `custom/scripts/tasks/ansible/wireguard_keys/` — key generation/allocation shared by both playbooks, split into four task fragments (all included via `ansible.builtin.include_tasks` with an explicit `{{ playbook_dir }}/../../custom/scripts/tasks/ansible/wireguard_keys/<file>.yml` path, not `ansible.builtin.include_role` — see the `custom/` note above for why):
  - `vm_key.yml` — generates just the VM's own WireGuard keypair (`wg genkey`/`wg pubkey` shelled out via `ansible.builtin.shell`, `args.executable: /bin/bash` since the pipeline needs `pipefail` and `/bin/sh` on this system is dash), idempotent via `creates:`. `control-panel/debian.yml` calls this unconditionally on every build; `add-peer.yml` calls the exact same file (it needs the VM's public key to render its own `wg0.conf`), so whichever one runs first actually generates the keypair, and the other just sees `creates:` already satisfied.
  - `generate_one_peer_slot.yml` — batch-creates N anonymous peer slots (keypair + PresharedKey + an IP address derived from an incrementing `peerN` directory name) under `custom/generated/keys/wireguard-keys/wireguard_peers/`, called in a loop by `control-panel/debian.yml` based on `peer_slot_count`. Deliberately produces *unclaimed* material only — which machine eventually uses a given slot is a separate concern, handled by the next two files.
  - `claim_peer.yml` — picks the first not-yet-claimed peer slot (glob + check for a `claimed` marker file) and returns its name as `claimed_peer_name`. Does **not** write the marker itself.
  - `mark_peer_claimed.yml` — writes the `claimed` marker for a given peer name, passed in as `peer_to_claim`. Deliberately split from `claim_peer.yml`: the marker is only written after the caller's own setup (reading the keys, rendering `wg0.conf`, `wg-quick up`) has actually succeeded, so a mid-flow failure doesn't permanently waste a peer slot — `add-peer.yml` calls this right after each of its two tunnels (WSL2, native Windows) is confirmed working, not right after `claim_peer.yml` returns.
- `custom/template/wireguard_control_panel/wg0.conf.j2` — the VM's own `wg0.conf` (server: `Address = 10.105.0.1/24`, `ListenPort`, one `[Peer]` block per currently-existing peer slot, claimed or not). Rendered into `custom/generated/preseed/<vm_name>/wg0.conf` by `control-panel/debian.yml`, injected into the ISO the same way the SSH host key is, copied to `/etc/wireguard/wg0.conf` by preseed's `late_command`, unconditionally, every build.
- `custom/template/wireguard_agent/wg0.conf.j2` — the control node's own `wg0.conf` (peer: `Address = 10.105.0.2/24`, `PersistentKeepalive`). Rendered directly to `/etc/wireguard/wg0.conf` on the control node itself by `playbook/wsl/add-peer.yml` (the only playbook in this repo that touches the machine running Ansible rather than `custom/` output or a remote host — needs `become: true` for the apt install and the `/etc/wireguard/` write). Its `[Peer]` block's `Endpoint` is deliberately left commented out — the VM hasn't booted yet at build time, so its eventual DHCP IP is unknown; `add-peer.yml`'s final `debug` task tells the user to fill it in and `wg-quick up wg0` manually once the VM's IP is known, mirroring the existing manual `known_hosts` IP fill-in step.
- Inside `preseed.cfg.j2`, the `wireguard-tools` package and the `late_command` lines that copy `wg0.conf`, enable `wg-quick@wg0`, rewrite `sshd_config`'s `ListenAddress` to `10.105.0.1`, and drop a `ssh.service.d/wireguard.conf` systemd override making `ssh.service` `After=`/`Requires=` `wg-quick@wg0.service` are all plain, unconditional lines — no Jinja conditionals at all. (An earlier, opt-in version of this feature needed a Jinja-conditional version of this block and hit a real whitespace-handling bug doing it — `trim_blocks`/`lstrip_blocks` eating the newlines around `{% if %}`/`{% endif %}` and silently corrupting the `\`-continued `late_command` string — that whole problem disappeared along with the conditional when WireGuard became mandatory; it's not a concern in the current unconditional code.)
- **Safety tradeoff, explicitly accepted by the user**: making `ssh.service` depend on `wg-quick@wg0.service` means that if WireGuard fails to come up for any reason, `sshd` never starts — and since `charlie` has no password and root login is disabled, there is *no* fallback login path at all, not even via the ESXi console. The user's reasoning: this VM is already a disposable, rebuild-from-scratch-if-broken environment by design (no rescue path even without WireGuard) — this just extends that same accepted tradeoff to one more subsystem, not a new category of risk. An earlier, safer alternative (firewall rule restricting the SSH port to the `wg0` interface instead of binding `sshd` to the tunnel address, so a down WireGuard interface means "unreachable" rather than "won't start") was offered and explicitly declined in favor of the simpler literal approach.
